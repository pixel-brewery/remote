# @pixel-brewery/remote-browser

Same-origin browser adapters for the headless Remote client. The host serves the application's packaged web assets and registered operations on the same origin. Browser pairing uses an HttpOnly device cookie; JavaScript never receives a native bearer credential. Redirects and caller-provided authority headers are denied.

Compose `BrowserRemoteConnector` with the exact document origin and a bound `window.fetch`. Create `RemoteSession` with the expected product/installation identity, connector, `createBrowserClock(window)` and `() => createBrowserOperationId(crypto)`. Imports perform no browser I/O. Initialization verifies host metadata and restores the cookie session; product requests preserve streaming and cancellation.

`BrowserPairingLocation` reads the shared `#pair=...&app=...&host=...&expires=...` invitation and rejects duplicate fields. The fragment is never sent in HTTP requests. Clear it after a durable successful pairing, keeping pending attempts recoverable. `createBrowserOperationId()` uses `crypto.getRandomValues`; it works in an HTTP LAN document without requiring secure-context-only `crypto.randomUUID()`.

The generic byte-port uses `requestBodyMode: 'buffered-http1'` by default: Chromium Fetch upload streams require HTTP/2 or HTTP/3, so ordinary HTTP/1 LAN and protected loopback requests use a bounded payload prepared before one dispatch. `maximumBufferedRequestBytes` defaults to 8MiB; exceeding it fails before networking, and cancellation stops body preparation. Set `requestBodyMode: 'streaming-fetch'` explicitly only for a supported browser/server combination. There is no retry-after-failed-stream fallback and no mutation replay. See [Chrome's request-streaming restrictions](https://developer.chrome.com/docs/capabilities/web-apis/fetch-streaming-requests).

This byte-port limit does not patch or replace the application's existing HTTP client. Normal same-origin `fetch`, XMLHttpRequest, FormData, File and Blob uploads continue through the original host/native-gateway request body, with product route limits and native streaming/cancellation. Response bytes, SSE, WebSockets and media Range remain streaming paths.

`readRemoteServerEvents()` incrementally parses UTF-8 SSE across chunk/CRLF boundaries and bounds retained event bytes. It does not infer JSON or event replay. `BrowserRemoteEvents` supplies bounded same-origin WebSocket lifecycle and read-reconciliation callbacks without queuing or replaying writes. Products validate event payloads and own domain caches.

## Application gate

`BrowserRemoteApp` is the generic pre-framework gate. Construct it once per document with the application's `appId`, the `window`, its exact `localOrigins` (for example an embedded local host), a `readCapabilities(session, signal)` function that reads and validates the application's own metadata through the authorized session, and optional native `controls` and `scanner`. Subscribe, call `attach()` and `prepare()`, then compose the application on `normal` or `ready`; render the connection view for `preparing`, `pairing-required` and `error` (`connection`, `invitation` or `capabilities`).

Local origins start normally without a probe. A packaged client with native controls starts normally unless the document is its protected `http://127.0.0.1:<port>` view. A start is remote only with an invitation fragment or native controls; otherwise any probe answer other than a JSON host descriptor (missing route, refused redirect, error or HTML page, network failure) keeps the ordinary start and publishes no intermediate phase. A remote start restores or completes cookie pairing, caches only the public attempt identifier in `sessionStorage` for recovery after a lost response, clears the fragment after `ready`, and reads the metadata before publishing `ready`. The deadline (default 15 s) fails as `connection`. While ready, `identity`, `origin`, `metadata` and `session` describe the host; confirmed revocation or `recheckAuthorization()` after an application 401 publishes `pairing-required` without replaying the failed request.

`pair(address, deviceName)` opens a copied invitation; a link to the same page prepares again. With native controls, `pair`, `scanAndPair` and `openConnection` validate the returned loopback view (exact `127.0.0.1` origin with port, not a local origin, matching identity and connection) before navigating. `leave()` closes the saved connection of the host last made ready. `attach()` prepares again for a new `pair=` fragment, disposes on `pagehide` and reloads a disposed page restored from the back-forward cache; it returns a detach function. The gate never polls. `readRemoteJson()` reads one bounded JSON product response and always releases it.

## Local host control

`RemoteHostControlClient` talks to an application's private host-control endpoint (default prefix `/__host/remote/v1`): `status()` GET, and `enable()`, `disable()`, `reconcile()`, `pair(endpointId?)` and `revoke(deviceId)` POST with `{}`, `{ endpointId }` or `{ deviceId }`. Calls use same-origin credentials, refuse redirects, bypass the cache, honour an optional `isAvailable()` guard before dispatch, a deadline (default 15 s) and a response bound (default 256 KiB), and validate every answer with `remoteHostStatusSchema` or the canonical bootstrap schema. Failures are `RemoteHostControlError` values with a `code`, the HTTP `status` and any canonical `remoteCode`. A failed mutating command may already have saved its intent, so read `status()` again. `createPairingUrl(bootstrap, status)` checks the invitation against that status (application, installation, advertised origin, expiry within five minutes) and returns the secret pairing URL. The client is stateless apart from one abort controller per call; `dispose()` aborts them.

HTTP LAN is explicitly unencrypted. Access requires the user-selected local network and one-time invitation, followed by a scoped device grant. The SDK includes no product domain, certificate, signing key or cloud issuer. Applications may supply their own HTTPS infrastructure later. Browser camera, service-worker and other secure-context features are not assumed; native QR scanning is provided by the Capacitor adapter.

Run `yarn nx run remote-browser:build`, `:typecheck` and `:test`. Focused tests cover same-origin admission, protocol-body cancellation, credential exclusion, bounded SSE, HTTP-safe IDs, the application gate's start classification, pairing recovery, revocation and lifecycle attachment, and the host-control client's bounds and failure classes. The shared browser/Electron/mobile acceptance UI lives in `apps/fixture-browser`.
